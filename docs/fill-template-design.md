# PDFテンプレート差し込み 基本設計



- 文書状態：**確定**（2026-10-19 Human承認）
- 対象：[`amane-pdf-api`](https://github.com/kooiei-in4a/amane-pdf-api)（main `f0c1c93`）、[`amane-tools-site`](https://github.com/kooiei-in4a/amane-tools-site)（main `882d838`）
- 経緯：設計案 → Claudeの独立レビュー（実測を含む）→ Codexの再レビュー → Human承認。経緯は12章。
- この文書は#77で追加済み。#78でAPIを実装し、実装時に確定した比較方法・上限の適用順序・エラーの判断を反映した。以後の設計変更もこの文書へ反映する。

## 1. 目的

既存のPDFテンプレートの指定位置に、利用者が入力した文字を配置し、完成PDFをダウンロードできるようにする。利用例は請求書・見積書、証明書・認定書、申請書などの定型文書。

次の2方式に対応し、どちらも同じAPIを使う。

1. **サービス提供テンプレート**：サイトがPDFと差し込み位置の定義を用意する。
2. **ユーザーアップロード**：利用者がPDFをアップロードし、画面で差し込み位置を指定する。

初版は**固定レイアウトへの文字差し込み**だけを扱う。

## 2. 前提（確認済みの現行構成）

- API：.NET 10。描画は pdfcpu 0.16.2 + BIZ UDPゴシック v1.051、合成・検証は qpdf 12.3.2。DB・認証・永続保存なし。
- 共通描画基盤 `PdfOverlayBuilder` が、入力検査、表示上のページ寸法の算出（CropBox・Rotate・UserUnitを反映）、白紙レイヤーの作成、qpdfでの重ね合わせ、属性の復元、出力検査を行う。透かし・ページ番号・押印で検証済み。
- サイト：.NET 10 / Blazor / PostgreSQL。PDF中継（`PdfRelay`）はブラウザから届いたmultipartをそのまま転送する。pdf.js 6.3.289 によるプレビューと、黒塗りの矩形指定UI（`pdf-redact-regions.js`）がある。
- 座標は黒塗りと同じく「表示上のページ左上を原点とする0〜1の値」で扱う。

## 3. 責務分担

| 対象 | 責務 |
|---|---|
| サイト | テンプレート資材の管理、プレビュー、矩形指定UI、入力フォーム、金額計算などの業務ルール、定義と入力値の合成、送信前の文字・はみ出しチェック、認証・利用回数、中継、ダウンロード |
| API | 入力の検証、座標の変換、文字の配置計算、描画、合成、出力の検証、一時ファイルの削除 |

- APIはテンプレートの出所を区別しない。テンプレートの保存・ID解決・DBは持たない。
- 業務ルール（税額、端数処理、日付書式など）はサイトで確定させ、APIは完成した文字列を描くだけにする。

## 4. 初版の範囲

**対象**

- 暗号化されていない通常のPDFの既存ページに、指定した矩形内へ文字を重ねる。
- 複数ページ・複数項目への差し込み。
- 文字サイズ、左・中央・右揃え、明示した改行。
- サービス提供テンプレート（請求書・見積書・証明書など少数）の選択と入力。
- PDFのアップロード、矩形の指定、値の入力、完成PDFの確認とダウンロード。

**対象外**：8章の制約一覧を参照。

## 5. API契約

```text
POST /api/pdf/fill-template
Content-Type: multipart/form-data

file    PDF（filenameあり、1件）
fields  UTF-8 JSON（filenameなし、1件）
```

- queryは受け付けない。partの順序は自由。未知・重複・欠落のpartは400。
- 成功時は `200 OK`、`application/pdf`、固定ファイル名 `filled.pdf`。

### 5.1 `fields`

```json
[
  {"page":1,"x":0.15,"y":0.2,"width":0.6,"height":0.04,"fontSize":12,"align":"left","text":"株式会社サンプル"},
  {"page":1,"x":0.65,"y":0.1,"width":0.25,"height":0.03,"fontSize":10,"align":"right","text":"2026年10月19日"}
]
```

| key | 規則 |
|---|---|
| `page` | 1始まりの整数。先頭0なし。PDFのページ数を超えたら400 |
| `x` `y` `width` `height` | 0〜1、小数点以下4桁まで、指数・符号・文字列は不可。幅・高さは正、矩形全体がページ内（`x+width≤1`、`y+height≤1`） |
| `fontSize` | 6〜72（pt）、小数点以下1桁まで |
| `align` | `left` / `center` / `right` |
| `text` | 6.2の文字規則に従う文字列 |

- 各要素のkeyは上記8つちょうど。未知・重複keyは400。
- 解析は `RedactRegions.cs` と同じ厳格な方式（strict UTF-8、BOM拒否、深さ制限、数値は文字列表現で検査）。
- 空欄の項目はサイトが送らない（`text` が空なら400）。
- 項目同士の重なりは許す。

### 5.2 上限

| 項目 | 上限 | 違反時 |
|---|---|---|
| PDF | 50 MiB（`MaxFileBytes`） | 413 |
| `fields` | 64 KiB | 413 |
| request全体 | MaxFileBytes + 64 KiB + multipart余白64 KiB（専用MaxFillTemplateRequestBytes） | 413 |
| 項目数 | 200件 | 400 |
| 1項目の文字数 | 200（UTF-16） | 400 |
| 1項目の行数 | 5行 | 400 |
| 1ページの描画要素数（1行＝1要素） | 100件 | 400 |
| 描画範囲 | 最初の項目のページ〜最後の項目のページで1000ページ以内（`OverlayMaxPages`） | 422 `too-complex` |

全描画要素は最大1,000件（200項目×5行）で、既存の全体上限4,000件の範囲内。`PdfcpuProcessor` の `MaxTextsPerPage`（4）・`MaxTextLength`（128）は呼び出し元ごとに指定できるようにし、既存APIの値は変えない。上限値は実装時の負荷試験（10章）で最終確認する。

### 5.3 エラー

| HTTP | reason | 条件 |
|---|---|---|
| 400 | — | multipart・JSON・key・数値・座標の不正、上限超過（件数・文字数・行数・ページ要素数）、使えない文字・禁止した並び、ページ番号超過 |
| 413 | — | PDF・`fields`・request全体のサイズ超過 |
| 422 | `field-overflow` | 文字が矩形に収まらない（ページ寸法が分かってから判定） |
| 422 | `form-fields` | フォーム・署名関連の構造を含むPDF（6.5） |
| 422 | `too-complex` | 処理上限の超過 |
| 422 | `unsupported-pdf` | 対応外のページ属性（既存と同じ） |
| 422 | なし | 破損・警告・暗号化PDF（既存と同じ） |
| 500 | — | 描画・出力検証の失敗 |
| 503 / 504 | — | 処理枠不足 / 30秒超過（既存と同じ） |

`field-overflow` では失敗した項目番号を返さず、固定文言とreasonだけを返す（#78実装時に確定）。サイトが送信前に項目ごとの検査を行う。

## 6. 描画方式

### 6.1 文字表（APIとサイトで共用）

- 固定TTF（sha256 `595dfefa…2673`）から、開発時スクリプトで表を生成する。透かし用の `WatermarkGlyphs.g.cs` とは別の表とする（透かしは5範囲・10,051字に限られ、`① ㈱ ￥ ※ 〒` などを含まないため）。
- 内容：使える文字の集合、各文字の送り幅（pdfcpuと同じ `送り幅×1000/2048` の切り捨て、1/1000 em単位）、字形番号（GID）。
- 収録しないもの：字形がない文字（多くの絵文字を含む）、補助平面の文字、異体字セレクタ、改行以外の制御文字、**ほかの文字と字形を共有する文字**（このフォントでは U+02DC/U+0303 と補助平面の1組のみ。文字対応表の曖昧さをなくすため）。
- サイトへは、既存の `pdf-watermark-glyphs.js` と同じく、API commit・フォントsha256・データsha256付きで生成・同期する。

### 6.2 文字規則

- 文字表に含まれる文字と、改行（LF）だけを使える。CRは400。
- 禁止する並び：`%` の直後の `p` `P` `t` `v`、`\` の直後の `n`（pdfcpuが置換・改行してしまうため）。
- 空白だけの項目は400。表にあるUnicode White_SpaceはU+0020・U+00A0・U+3000で、LFとこれらだけの項目を拒否する。trim・Unicode正規化はしない。

### 6.3 配置計算（APIが行う）

pdfcpuの折り返し・揃え・`width` 機能は使わない（重なり・押し戻し・切れを実測で確認したため）。APIが行ごとに位置を計算し、1行を1要素・左揃えでpdfcpuへ渡す。

- 単位は表示上のpt。矩形はページの表示寸法（`PdfPageAttributes.DisplayWidth/Height`）から求める。
- `s` を文字サイズとする。
- 左右の内側余白：各 `0.05 s`（送り幅をはみ出す字形は6字のみ、最大0.047 em。実測）。
- 行幅：表の切り捨て送り幅の合計 × `s` / 1000（pdfcpuが `/W` に書く値と同じ）。
- 横方向：`left` は矩形左端+余白、`right` は矩形右端−余白−行幅、`center` は矩形中央−行幅/2。
- 行間：`1.2 s`（固定）。
- 必要な高さ：`s + 1.2 s ×（行数−1）`。字形は縦方向に文字サイズ分の枠へ収まる（上端0.880 em、下端−0.120 em。実測）。
- 収まりの判定：最大行幅 ≤ 矩形幅 − `0.1 s`、かつ 必要な高さ ≤ 矩形の高さ。満たさなければ422 `field-overflow`。比較と配置式にはdecimalを用い、表示寸法を一度decimalへ変換する。pdfcpuへ渡すときだけdoubleへ変換する。ちょうど収まる値・0.1 pt超過をテストで固定する。自動縮小・自動折り返しはしない。
- 縦方向：行のまとまりを矩形の中央に置く。各行のベースライン = その行の文字枠の上端 − `1802/2048 × s`。
- pdfcpuへ渡す座標 = ベースライン − `ceil(246/2048 × s)`（文字枠の下端。実測）。非負なら `pos.y` に設定する。負の `pos.y` はpdfcpuがページ中央指定として扱うため、負の場合だけ `pos.y=0`、`dy=計算した座標` として同じ実座標を渡す（#78の境界実測で送信表現を変更）。anchorは使わない。この式と負座標の分割を単体・実content streamで固定し、pdfcpu更新時に検出する。
- 色は黒、回転なし、フォントは固定。

### 6.4 `%` の受け渡し

連続する n 個の `%` を n+1 個に書き換えてpdfcpuへ渡す（実測で元の文字列どおりに出力されることを確認）。`PdfcpuProcessor.WriteLayerAsync` で行い、`ValidateText` の `%` 拒否はこの書き換えに置き換える。文字数上限は書き換え前のUTF-16長に適用し、書き換え後はJSON全体のbytes予算で制限する（例：`%a`×100は元200単位、書き換え後300単位）。既存APIは入力時に `%` を拒否するか固定のページ番号を生成するため、外から見える挙動は変わらない。

### 6.5 フォーム・署名の検出

入力時のメタデータ読み取り（`PdfPageBoxes`、qpdf JSONの全オブジェクトを読み込み済み）で、追加のqpdf呼び出しなしに検査する。各オブジェクトの値を**直接埋め込まれた辞書・配列・stream辞書まで再帰的にたどり**、次のいずれかがあれば422 `form-fields`。

- Catalogに `/AcroForm`（空でも拒否）または `/Perms` がある。
- いずれかの辞書が `/Subtype /Widget`、`/FT /Sig`、`/Type /Sig`、`/Type /DocTimeStamp` を持つ。

すべての署名構造を網羅的に検出できるとは保証しない。代表的な入力を拒否できることを検証で確認する（10章）。走査量は既存のmetadata上限（32 MiB・50,000 object・深さ64）の範囲内。

### 6.6 処理の流れ

1. multipartを読み、`fields` をupload完了後・tool起動前に検証する（400）。
2. `PdfOverlayBuilder` が入力PDFを検査し、metadataを読む。ここでフォーム・署名を検出する（422）。ページ番号の上限を確認する（400）。
3. ページ寸法から矩形と配置を計算し、収まりを判定する（422 `field-overflow`）。描画範囲は最小〜最大のページ。
4. pdfcpu `create` でレイヤーPDFを作る。文字抽出にはpdfcpu 0.16.2以降のToUnicodeを使う。100種を超える字形を含む複数ページのMuPDF・Poppler抽出、Type0がちょうど1つ、bfcharの各ブロックが1〜100件で宣言数と実件数が一致、描いた全GIDと元文字の対応をCIで検証する。全11,425字の対応も別途検証する。
5. 既存の生成物検査、重ね合わせ、属性復元、出力検査を行う。
6. 成功・失敗・キャンセルのいずれでも一時ファイルを削除する（既存）。

2026-10-19のHuman決定により、PR #83の実測を根拠に独自のToUnicode再作成を削除した。容量管理・生成物検査・キャンセル時のprocess終了待ち・後始末は共通処理を使い、job上限124 MiBを維持する。

### 6.7 ログ・機密性

PDF本文、`text` の値、利用者のファイル名をログ・Problem Detailsに出さない。`text` はargvに載せず、0600のJSONファイルだけでpdfcpuへ渡す（既存方式）。

## 7. サイト

### 7.1 共通

- 中継のツール定義を追加する（ApiPath `/api/pdf/fill-template`、PDF共通の日次枠）。
- **利用回数の返却（2026-10-19 Human承認）**：上流の400は一律に返却する（query検証で `RefundBadRequest: true`）。422は `field-overflow` だけ返却する（`RefundedProblemReasons`）。`form-fields`・`too-complex`・`unsupported-pdf`・reasonなし422は返却しない。`docs/tool-usage-limits.md` のHuman決定の例外へ追記する。
- 送信前チェック：6.1の文字表で、使えない文字・禁止した並び・行数・文字数・はみ出しを入力中に表示する。はみ出す場合は文字サイズを下げる提案を出す。送信ボタンは問題がある間は無効にする。
- 生成結果は取得した完成PDFをpdf.jsで表示する（ブラウザ内の仮描画を最終結果とみなさない）。二重送信防止、Blob URLの破棄は既存方針どおり。

### 7.2 ユーザーアップロード方式

PDF選択 → pdf.jsプレビュー → 矩形の指定（黒塗りUIを流用） → 項目ごとに文字サイズ・揃え・文字を入力 → 生成 → 完成PDFの確認 → ダウンロード。テンプレートの保存はしない（毎回アップロード）。

### 7.3 サービス提供テンプレート方式

- テンプレートはサイトRepositoryの静的資材（PDF＋定義JSON）としてversion管理する。管理画面・DBテーブルは作らない。
- ブラウザが資材を取得し、定義と入力値から `fields` を組み立て、ユーザーアップロード方式と同じ中継へ送る（サーバー側に新しい処理経路を作らない）。
- 定義JSONの形式はサイト内部のもの（項目key、表示名、矩形、文字サイズ、揃え、最大行数など）。資材のテストで、PDFのsha256・ページ寸法との一致、矩形がページ内であること、テンプレートPDFにフォーム・署名構造がないこと、見本値が収まることを確認する。
- テンプレートPDFは自作で権利上問題のない様式に限る。
- 開発順序：矩形指定UI（7.2）を先に作り、それを使って定義JSONを作成する。

## 8. 制約一覧（Issue・READMEに明記する）

### 入力PDF

| 制約 | 理由 | 将来の扱い |
|---|---|---|
| フォーム・署名関連の構造（AcroForm、入力欄、署名、文書タイムスタンプ、`/Perms`）を含むPDFは非対応（422 `form-fields`）。すべての署名構造の検出は保証しない | 差し込み文字が入力欄に隠れる。署名を黙って無効にする | 焼き込み（API #32）と合わせて検討 |
| 暗号化PDFは非対応（422） | 既存の重ね合わせの方針 | パスワード解除後に利用 |
| 注釈（コメント等）は差し込み文字より前面に表示される | 既存の重ね合わせ方式 | 必要なら焼き込み |
| PDFの無害化・匿名化はしない（メタデータ・添付・JavaScriptなどは残る） | 自動で破壊的な加工をしない | 情報除去ツールを案内 |
| PDF/Aの適合性は保証しない | 未検証 | 需要があれば検証 |
| 50 MiB、描画範囲1000ページ、30秒、同時2件 | 既存の上限 | 実測で見直す |

### 文字

| 制約 | 理由 | 将来の扱い |
|---|---|---|
| 固定フォントに字形がある文字だけ（400） | 字形がない文字はpdfcpuが黙って落とす | — |
| 補助平面の文字（𠮷・多くの絵文字など）・異体字セレクタ・改行以外の制御文字は不可 | フォントにない、またはpdfcpuが扱わない | フォント追加時に検討 |
| `%p` `%P` `%t` `%v` と `\` + `n` の並びは不可（400） | pdfcpuが置換・改行する | 需要があれば分割描画 |
| 結合文字の濁点（NFD）は独立した全角幅の濁点として描かれる | 正規化しない方針 | サイトで警告を検討 |
| `\`（U+005C）はバックスラッシュとして表示され、円記号にならない | フォントの字形どおり | サイトで案内 |
| フォントはゴシック1種、色は黒、横書きのみ、回転なし | 初版の範囲 | 需要に応じて |

### 配置

| 制約 | 理由 | 将来の扱い |
|---|---|---|
| はみ出しはエラー（422 `field-overflow`）。自動縮小・自動折り返しなし | 黙って切れる・重なるのを防ぐ | サイトで縮小を提案 |
| 縦位置は中央、行間は1.2文字分、左右に0.05文字分の余白（固定） | 仕様を単純にする | 需要に応じて指定可能に |
| 1項目5行まで | 上限の明確化 | 実測で見直す |

### 機能

| 制約 | 理由 |
|---|---|
| 明細行の追加・自動改ページなし。明細はテンプレートの固定行数まで | 初版は固定レイアウトのみ |
| テンプレートは保存しない（毎回アップロード） | 永続保存しない方針 |
| 画像・印影の差し込み、AcroForm/XFAへの入力、PDF内の文字置換、HTML等からの生成、定期発行・一括出力はしない | 初版の範囲外 |
| 電子署名・真正性の保証はない | 対象外 |
| 日次回数は他のPDFツールと共通の枠 | 既存の利用制御 |

### 運用

- pdfcpu・フォントを更新するときは、文字抽出・字幅・ベースラインの検証をやり直す。ToUnicodeの対応・100件境界と100種を超える字形の抽出をCIで継続検証する。

## 10. 検証計画

- **配置**：A4縦・横、A3、CropBox原点ずれ、Rotate 90/180/270、UserUnit 2、寸法混在で、左・中央・右揃えと複数行の位置が計算どおり（変換行列と、Popplerでの描画の両方）。
- **文字抽出**：100種を超える字形を含む複数ページで、MuPDFとPoppler（`pdftotext`）の両方で全文字が正しく抽出できる。
- **文字**：`%` を含む文字列（末尾・連続・数字の前）が元のまま出力される。禁止した並び・使えない文字が400になる。文字表の照合（全収録文字を実pdfcpuで描いて欠落がないこと、字幅の一致）。
- **はみ出し**：境界値（ちょうど収まる／0.1 pt超える）で判定が正しい。
- **フォーム・署名**：承認署名、DocMDP（認証署名）、文書タイムスタンプ、UR3（Reader拡張）、入力欄のみ、XFA、空の `/AcroForm`、AcroFormから参照されない直接埋め込みのWidget注釈を、すべて422 `form-fields` にする。署名付きfixtureの作成手段を検証スクリプトに追加する。
- **既存APIへの影響なし**：透かし・ページ番号・押印・from-imagesの既存テストが通る。
- **負荷**：全1,000要素（1ページ100要素×10ページ）、異なる字形を最大限含む、文字サイズ72 pt、項目を1ページ目と1000ページ目に置いて描画範囲1000ページ、入力50 MiB、30秒・job容量・メモリの範囲内。参考値：100ページ×6,000要素で pdfcpu create 0.48秒・50 MB・レイヤー735 KB（初版の上限を満たす根拠ではない）。
- **サイト**：pdf.jsで指定した矩形と出力の位置の一致（UserUnitを含む）、送信前チェックとAPIの判定の一致、回数の返却。
