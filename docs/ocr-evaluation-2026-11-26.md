# OCR精度の前後比較と NDLOCR-Lite の処理コスト（2026-11-26）

この記録は文書と、測定に使った試料ZIPです。APIのソース、コンテナイメージ、依存関係は変えていません。NDLOCR-Lite の採用や新しいエンドポイントの追加も、この記録では行っていません。

現行のOCR仕様は[READMEのOCR節](../README.md#スキャンpdfの日本語ocrlinux)です。標準・高精度そのものの検索条件と密なページの処理時間は[ocr-quality-validation.md](ocr-quality-validation.md)にあります。ここにある数値は、記載した日付、commit、イメージ、試料、ホストでの結果です。

## 結論

11月24日より前のOCRと、2026-11-26時点の現行APIに、同じ合成PDFを渡して比べました。検索できる語は、中心の8試料で 16/85 から、標準 80/85、高精度 85/85 に増えました。90度・180度・270度のスキャンは、前は PDF.js でも PDFium でも 0/12 で、現行は両エンジンで 12/12 です。A3とA2は、前は HTTP 422 で、現行は処理できています。短い1行は、前も部分一致が1件あり、現行では2語とも検索できました。

NDLOCR-Lite 2.0.0 は、印刷物向けの別経路として測る価値があります。このマシンでモデルを読み込んだあとは、6コアで1ページ 0.79〜1.42秒、ピークメモリは約 1.0 GiB でした。今のAPIと同じ 1 CPU に絞ると 4.37〜7.95秒です。1.5 GiB の枠には1プロセスが収まりました。2プロセス分のメモリは収まりません。モデルの読み込みに約7秒かかるため、ページごとにプロセスを分ける使い方には向いていません。

今回の速度比較は、行数の少ない合成ページの「画像から文字」です。API応答時間（描画、認識、検索できるPDFの組み立て）とは別の数です。手書きの読み取りは対象にしていません。

## 1. 同じPDFでの検索ヒット

### 条件

ホストは Ubuntu、AMD Ryzen 5 5600G、メモリ 15 GiB です。コンテナは `--cpus 1 --memory 1536m --memory-swap 1536m` です。

| 時点 | イメージ | コミット |
| --- | --- | --- |
| 11月24日より前 | `amane-pdf-api-ci:1b04f3c44878aa6d7fa246b6191aa45edc05c78b` | `1b04f3c`。#117 直前の `main` である `0b91162`（`1b04f3c` の子）とは、`src` では `RenderSlot.cs` のコメント1行だけが異なる |
| 現行 | `amane-pdf-api:measure-6a8c3db` | `6a8c3db`（PR #132 のマージ）。ツリーは `37ebe2d` と一致 |

前のAPIは `direction` だけを受けます。現行は `quality=standard` と `quality=high` を分け、既定の `existingText=skip` のまま送りました。

指標は文字誤り率ではありません。PDF.js 6.3.289 の `PDFFindController` で、指定した語が1回以上見つかった数です。回転したスキャンは、イメージ同梱の PDFium でも同じ語を探しました。試料は `scripts/ocr-search-validation.py` と同じ系統の合成PDFに、短い1行、文字が最初から入っているPDF、A3、A2を足したものです。

入力と、11月24日より前の出力は [ocr-evaluation-2026-11-26-samples.zip](ocr-evaluation-2026-11-26-samples.zip) にあります。SHA-256 は `b91ef43c2852c8604dd8eea6879a16c0944f427d38692ab85a6ea31b30d86138` です。`inputs/` が両方のAPIに渡した20件、`outputs/` と `results.json` は前のAPIの結果です。A3とA2は前のAPIが 422 で返したため、`outputs/` にはありません。現行の出力PDFはこのZIPに含めていません。速度比較のPNGは、`inputs/horizontal.pdf`、`inputs/vertical-with-heading.pdf`、`inputs/ruled-invoice.pdf`、`inputs/shadow.pdf` を `pdftoppm -r 300 -png -singlefile` で、`inputs/a3-portrait.pdf` を `pdftoppm -r 287 -png -singlefile` で作りました。測定用のワンオフスクリプトはリポジトリに含めていません。

## 2. NDLOCR-Lite の速度、メモリ、CPU

### 条件

対象は [NDLOCR-Lite](https://github.com/ndl-lab/ndlocr-lite/) 2.0.0、ONNX Runtime 1.31.1、CPU実行です。Python は 3.13.9 です。モデル4ファイルは事前に取得し、SHA-256 を確認しました。合計 157,416,207 バイトです。

比べた画像は、上の精度比較で使った入力のうち5ページをPNGにしたものです。横書き、縦書き、請求書、影付きを 300 dpi（2481×3508）、A3縦をAPIの1,600万画素上限に合わせた 287 dpi（3357×4746）にしました。NDLOCR が数えた行数は、順に 3、6、44、9、4 です。密な書籍の1ページではありません。

Tesseract は現行イメージの中で、APIの `RecognizePageAsync` と同じ言語、PSM、Sauvola、1スレッド、アドレス空間 384 MiB で実行しました。出力は TSV だけです。APIが追加で書く text-only PDF と hOCR は含みません。NDLOCR は JSON だけです。どちらも文字を返し、この5枚では文字数が 73〜207 字の範囲で揃っていました。これは途中で落ちていないことの確認であり、精度の採点ではありません。

NDLOCR の認識モデルは演算スレッドを1に固定し、行をスレッドプールで並列にします。1 CPU のコンテナでも、プロセスから見えるコア数は6のままでした。CPUの上限は cgroup で掛けています。ONNX Runtime は仮想アドレス空間が実メモリより大きくなり得るため、NDLOCR には Tesseract の 384 MiB アドレス空間制限を掛けていません。

### モデルを読み込んだあとの1ページ

| ページ | Tesseract 標準 | Tesseract 高精度 | NDLOCR 6コア | NDLOCR 1 CPU |
| --- | ---: | ---: | ---: | ---: |
| 横書き | 0.70秒 / 162 MiB | 1.08秒 / 219 MiB | 0.79秒 | 4.37秒 |
| 縦書き | 0.72秒 / 131 MiB | 1.53秒 / 190 MiB | 0.81秒 | 4.66秒 |
| 請求書 | 0.95秒 / 163 MiB | 1.92秒 / 210 MiB | 1.42秒 | 7.95秒 |
| 影付き | 0.98秒 / 162 MiB | 1.67秒 / 219 MiB | 0.89秒 | 4.91秒 |
| A3 | 0.99秒 / 238 MiB | 1.66秒 / 288 MiB | 0.94秒 | 4.74秒 |

Tesseract のメモリは、1 CPU・1536 MiB のコンテナで `memory.current` を10ミリ秒間隔に見た最大値です。全件が終了コード0で、384 MiB のアドレス空間制限では止まっていません。CPU時間は壁時計とほぼ同じで、1コアを使い切っています。

NDLOCR の秒数は、プロセスがモデルを読み込んだあとにツール自身が報告した計算時間です。6コアの常駐プロセスは、5ページと読み込みを合わせて壁時計 11.47秒、CPU 32.37秒（平均 2.8コア）、最大 RSS 1,036 MiB でした。1 CPU・1536 MiB・スワップなしのコンテナでは、壁時計 33.60秒、CPU 33.90秒、最大 RSS 1,031 MiB で、OOM にはなっていません。cgroup のメモリを50ミリ秒間隔で見た最大は 976 MiB で、RSS のピークより短い間隔の山を取り逃している可能性があります。

モデル4本の読み込みは 6.3〜7.0秒でした。ページごとにプロセスを起動した6コアの測定では、壁時計 7.19〜8.08秒、最大 RSS 696〜762 MiB です。内訳のほとんどは読み込みです。

待機中のAPIプロセスは、同じ 1 CPU・1536 MiB のコンテナで RSS 約 74 MiB でした。この値は待機中だけで、描画（PDFium の DATA 上限 384 MiB）や PDF の組み立ては含みません。NDLOCR とは同時に動かしていません。描画と認識を順に行う前提で、別々のピークを足すと、APIと NDLOCR 1本は 1.5 GiB に収まる計算です。NDLOCR を2本同時にすると超えます。

### この結果から置けること

印刷された短いページを、モデルを常駐させて1件ずつ処理する別経路なら、このマシンでは動きます。今の 1 CPU・1.5 GiB のまま、Tesseract の横にそのまま追加できる処理量ではありません。検索できるPDFを返すには、NDLOCR の座標から文字層を組み立てる処理が別に必要です。その実装はこの記録に含めていません。

公開されている精度は、今回の5枚では測っていません。印刷物の F値は [evaluation_jptype.csv](https://github.com/ndl-lab/ndlocr-lite/blob/master/evaluation_jptype.csv) の中央値で、ver.1.2.1 が 0.9718（0.971774879）、今回使った ver.2.0.0 が 0.9691（0.969091068361031）です。手書きは README の「手書き文字に対する評価(NDLOCR-Lite ver.2.0.0)」で、JaWildText の手書き 1,065 ファイルに対する全体 CER（中央値）0.1327、全体 F値（中央値）0.8927 です。今回の速度試料は手書きではありません。
