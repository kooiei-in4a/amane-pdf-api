# OCRの標準・高精度の検証（2026-11-26）

対象は [Issue #126](https://github.com/kooiei-in4a/amane-pdf-api/issues/126)、[Issue #128](https://github.com/kooiei-in4a/amane-pdf-api/issues/128)、[Issue #124](https://github.com/kooiei-in4a/amane-pdf-api/issues/124) のOCRです。APIの指定と上限は[READMEのOCR節](../README.md#スキャンpdfの日本語ocrlinux)に記載しています。

## 再現方法

Ubuntu 26.04、AMD Ryzen 5 5600G、Tesseract 5.5.0、qpdf 12.3.2 で実測しました。Dockerは `--cpus 1 --memory 1536m --memory-swap 1536m --read-only --tmpfs /tmp:rw,nosuid,nodev,noexec,size=256m` で起動しました。アプリは非rootで、同時実行上限2件、qpdf上限30秒の既定設定を使いました。Tesseractは1スレッド、1プロセスあたりの仮想メモリ上限384 MiBです。

```bash
docker build -t amane-pdf-api:ocr-quality .
npm ci --prefix scripts/ocr-search --ignore-scripts --omit=optional --omit=dev
python3 scripts/ocr-search-validation.py amane-pdf-api:ocr-quality --benchmark
```

検証ホストにPython 3、Pillow、Node.js、qpdfが必要です。`--benchmark` で密な文書4件の応答時間を測ります。`--quality standard` または `--quality high` で方式を指定できます。`--artifacts DIR` で検索試験の入出力PDFを確認できます。

## 短い1行の標準OCRで文字層が空になった回帰

**旧試料：標準0/8字・高精度8/8字。** レビューでは、PRの `d1d658d` のイメージを上記の本番相当のコンテナ制約で動かし、12 ptの「日本語の起動確認」だけを描いた旧スモーク試料で確認しました。両方式ともHTTP 200でした。標準では文字層が空になり、高精度では全文を認識しました。ページ番号だけ、署名欄だけ、短い1行だけの文書も、処理が成功したように見えたまま検索できない可能性があります。発生頻度は未計測です。[PR #127 のレビュー](https://github.com/kooiei-in4a/amane-pdf-api/pull/127#issuecomment-7179161029)

1. `scripts/docker-smoke.py` の `pdfcpu_smoke` と同じ手順で、`tests/Amane.Pdf.Api.Tests/Fixtures/pdfcpu-blank.json` を `qpdf --json-input` でPDFにし、`pdfcpu-layer.json` を `pdfcpu create` で重ねます。ページ下端中央に旧試料の1行が入ります。
2. `POST /api/pdf/to-images?format=png&dpi=200` のZIPからPNGを取り出し、`POST /api/pdf/from-images?quality=original` に渡して画像だけのPDFを作ります。
3. そのPDFを `POST /api/pdf/ocr?direction=horizontal&quality=standard` と `quality=high` に送り、HTTPステータスと出力PDFの文字層を比較します。
4. 同じ画像PDFからAPIと同じPDFiumレンダラーの `render-png` で300 dpiのPNGを得ます。標準の `jpn` で同じPNGをTesseractに渡し、`--psm 1`・`3`・`6` と `thresholding_method=0`・`1`・`2` を組み合わせてTSVを比較します。描画経路を比べる場合は、同じPDFを `pdftoppm -r 300 -png -singlefile` で描画し、同じ認識条件で比較します。

PDFiumのPNGでは、どのPSMでもSauvola（`thresholding_method=2`）のときだけ空になり、従来の二値化（`0`）と適応型Otsu（`1`）では全文を認識しました。文字をページ中央や上端に移しても同じ結果でした。比較した二値化画像の黒画素数は7,012と7,015で、文字の画素が残っていても認識段階で結果が空になりました。同じPDFを `pdftoppm` で300 dpiに描いたPNGでは、画素がほぼ同じでもSauvolaで全文を認識しました。[PR #127 のレビュー](https://github.com/kooiei-in4a/amane-pdf-api/pull/127#issuecomment-7179161029)

`thresholding_window_size=1.0` と `thresholding_kfactor=0.2` の組み合わせで1行の試料は回復しましたが、罫線付き請求書は29/34語で既存の合格基準を下回りました。ノイズ試料でも検証し、標準の横書きに `thresholding_window_size=0.2` と `thresholding_kfactor=0.3` を適用しました。1ページにつき1回の認識で短い1行を抽出できることを、複数行の文書とあわせてDockerスモークで確認しています。

## 横書きスキャンの回転と既存文字層（#124）

横書きは1回の認識でPDF・TSV・hOCRを出力します。TSVで語の順序と位置を取り、hOCRの `textangle` で行の角度を調べます。行を読む向きで文字の間隔を計算し、文字層を画像の向きに戻して配置します。180°ではPDFiumが同じ行の複数のテキストオブジェクトを左から右へ並べ替えるため、読み順と位置を保てるよう、連続した文字列を1つのテキストオブジェクトにまとめます。[TesseractのhOCR出力](https://github.com/tesseract-ocr/tesseract/blob/5.5.0/src/api/hocrrenderer.cpp)・[PDFiumの文字処理](https://github.com/chromium/pdfium/blob/main/core/fpdftext/cpdf_textpage.cpp)

A4・200 dpi・JPEG品質75の合成スキャンの画像自体を回転し、PDFの回転指定を使わずに `6636c57` で検証しました。各角度は標準・高精度の両方で、PDF.js 6.3.289と同梱PDFium（`chromium/8100`）で12/12語を検出しました。下表は、文字の画素の矩形と検索強調の矩形の重なりをIoUで測り、両方式・全語で最小の値を記載しています。

| 画像の回転 | 同梱PDFiumの検索矩形 | Chromiumで実行したPDF.jsの強調 |
| --- | ---: | ---: |
| 90° | 0.49 | 0.68 |
| 180° | 0.65 | 0.82 |
| 270° | 0.48 | 0.77 |

回帰試験は両エンジンでの全文検索、PDFiumの強調矩形のIoU 0.4以上、Popplerで72 dpiに描画した入力と出力の画素の一致を確認します。PDF.jsの強調表示は `scripts/ocr-search-validation.py --highlight DIR` と `scripts/ocr-search/highlight.mjs` で実ブラウザから測定できます。

既存文字の検査では、PDFiumの子プロセスからページ番号だけを返します。表示範囲に英字や日本語などの文字（UnicodeのLetter）が4字以上あれば、すでに検索できると判定します。画像の描画座標をページ座標に変換し、ページ表示範囲（MediaBoxとCropBoxの共通部分）と重なる面積を画像ごとに求めます。1枚の画像がその範囲の半分以上を覆うページでは、表示上の上下8%を除いた範囲で、透明なテキスト描画モード（`Tr 3`）の文字だけを数えます。本文内に入力値が2行あるスキャン、見出しと番号が付いたスキャン、画像がなくページ番号だけのページはOCRされることを確認します。短い既存OCR文字層、ロゴ付きの文書PDF、回転とCropBoxを持つ文書PDF、混在文書、全スキップ時のバイト一致、明示的にOCRを行う場合も統合テストで確認します。

## 小さい文字の罫線付き請求書（#134）

`small-ruled-invoice` は、A4 に22 ptのBIZ UDPゴシックの見出し、10〜11 ptのBIZ UDP明朝の本文、罫線付きの明細7行と小計・税・合計、振込先・支払期限を配置した合成請求書です。既存の `ruled-invoice` は36 px（200 dpiで約13 pt）で描画します。Pillowで#134の配置を直接描いた試料は `a181705` の標準でPDF.js 30/34語だったため、IssueのReportLab手順を採用しました。[Issue #134 の原稿・検索語](https://github.com/kooiei-in4a/amane-pdf-api/issues/134)

## 描画画像に応じた標準横書きの二値化（#136、初回の `65ff606`）

#135 の50組の比較は、PDFium で描いた1種類の JPEG に対する Sauvola の調整です。同じ原稿を poppler で描くと、`3c78ff5` ではその調整で23/34語、同じ JPEG を `from-images` でPDFにした場合は19/34語でした。今回の比較では、両方の描画経路で検索できる語の数を確かめました。

### 試料と判定

- #134 の ReportLab 原稿を poppler 26.01.0 の `pdftoppm -r 200 -gray -jpeg -jpegopt quality=75 -singlefile <原稿.pdf> <出力>` で描き、`small-ruled-invoice-poppler.jpg` として固定しました。SHA-256 は `cb1b2ffac416123954fc352ae52a64ee47540014cff164a751d29954705feb68` です。
- `small-ruled-invoice-poppler` は #134 の再検査と同じく、Pillow でその JPEG を RGB に変換し、200 dpi・品質75の画像PDFにします。`small-ruled-invoice-poppler-from-images` は同じ JPEG を `/api/pdf/from-images?quality=original` に渡した出力です。PDFium 版と poppler 版は標準で両方のビューアが30/34語以上を見つけることを必須とし、`from-images` 版も同じ34語を集計します。
- 描画 PNG を8×8区画に分け、各区画で8×8点の輝度を採ります。各区画の上位四分位点を背景の明度とし、その90パーセンタイルと10パーセンタイルの差を求めます。差が24以上（明度は0〜255）なら Sauvola（`method=2`、`window_size=0.33`、`kfactor=0.32`）を使います。影の試料では差が61、粒状感では12、請求書・点ノイズ・短い1行では0でした。
- 差が24未満のときは、16画素間隔で採った行と列で、輝度128未満の連続画素を数えます。連続区間が32個以上あり、そのうち長さ3画素以下の区間が35%以上なら、適応型 Otsu（`method=1`、`tile_size=0.5`、`smooth_kernel_size=0.03`、`score_fraction=0`）を使います。細い画線の割合は小さい請求書3種で42.8〜50.3%、既存の請求書で14.0%、表で9.1%、点ノイズで21.5〜21.8%でした。それ以外はページ全体に Otsu（`method=0`）を使います。
- Otsu を一律に使うと、小さい請求書は PDFium 版が24/23語、poppler 版が27/27語（PDF.js / PDFium）、影が9/12語でした。適応型 Otsu を全ページに使うと、請求書に有効な設定でも、例えば `tile_size=0.5 / smooth_kernel_size=0.03 / score_fraction=0` では表が7/9語、`2 / 0.03 / 0.1` では折り返した段落が0/3語でした。背景差に加えて、細い画線の割合を測る理由です。
- 0語だった標準横書きは1回だけ再認識します。初回が Sauvola なら Otsu、初回が Otsu または適応型 Otsu なら #128 の短い1行を回復した Sauvola（`0.20 / 0.30`）を使います。PNG の判定は追加ファイルを作らず、行バッファと固定個数の区画サンプルで行います。この版では高精度と縦書きに従来の設定を使いました。

## 高精度で上下逆さの出納帳を認識する（#138）

#137 の `bf4729a` を起点に、高精度で上下逆さの出納帳が0/18語になることを再現しました。同じ PDFium の描画 PNG を固定モデルの `psm 1` に渡すと、既定の Sauvola、標準の調整値、Otsu、適応型 Otsu のいずれでも高精度は0/18語でした。標準のモデルは同じ Sauvola で18/18語です。高精度の既定設定では Tesseract が向きの信頼度4.27を受け、横書きで非CJKと判定した文字を回転せずに認識していました。[Issue #138](https://github.com/kooiei-in4a/amane-pdf-api/issues/138)

## #154 横書きの小角度傾き補正

変更前は #153 と #155 を含む `45dace7`、変更後は傾き補正ありです。両方を同じ Tesseract 5.5.0・PDFium のコンテナで比較しました。

### API の認識経路

標準横書きの API が実際に渡した PDFium の PNG と Tesseract の TSV を、合成試料に限って一時的に捕捉しました。

| 試料 | API の TSV で語がある行・語 | Poppler の PNG を使った初回の行・語 | PDF での確認 |
| --- | ---: | ---: | --- |
| H2-strong | 3行・29語 | 4行・57語 | TSV の3行を確認。原稿の2・3行目の欠落と最終行の分割は認識時点で発生 |
| F3-strong | 初回0行・0語、再試行7行・12語 | 0行・0語 | TSV の7行を確認。再試行でも表の本文は生成されなかった |

両試料とも変更前は Sauvola を選び、独立した OSD の判定を経由しませんでした。F3-strong のみ空の結果を受けて、窓幅 0.20、kfactor 0.30 の従来の再試行に進みました。H2-strong では同じ標準設定の Tesseract が描画した画像によって行を異なる形に分割しました。TSV の非空行を `pdftotext -bbox` と `-raw` で照合し、文字層生成での行の欠落は確認されませんでした。補正後も両試料は Sauvola を選び、初回に H2-strong は4行・56語、F3-strong は表を含む10行・42語になりました。F3-strong の空結果による再試行は発生しませんでした。

### 推定と試料

300 dpi の横書き原稿と、管理番号・明細4件・合計を持つ架空の罫線付き帳票を生成しました。正負の角度は画像の右に向かって下がる傾きを正とします。鮮明版から回転、台形歪み、ぼけと JPEG 圧縮を加える手順は [deskew_samples.py](../scripts/ocr-search/deskew_samples.py) で再現できます。次のコマンドは、各試料の文字数、誤り数、欄の一致数、対応できた明細行、適用角度、応答時間を JSON Lines で出力します。

```bash
python3 scripts/ocr-search-validation.py <変更前のイメージ> --deskew-matrix
python3 scripts/ocr-search-validation.py <変更後のイメージ> --deskew-matrix
python3 scripts/ocr-search-validation.py <変更後のイメージ> --deskew-only --highlight /tmp/ocr-deskew-highlight
```

グレースケールを長辺900画素以下に縮小し、輝度160未満の画素を含む格子を射影します。2行離れた射影値の差の二乗和を、±10°を0.5°刻み、そのピークの周囲を0.1°刻みで評価します。採用には、最良角が0.8°以上、探索範囲の内側、0°のスコアの1.20倍超、1.5°以上離れた候補の最高スコアの1.08倍超が必要です。格子の墨が少なすぎる（40点未満または0.2%未満）、多すぎる（20%超）、回転で端の墨（輝度232未満）が切れる場合は補正を省きます。

新作試料の0.25°と0.5°は補正前からほぼ正しく認識でき、予備計測で0.5°の帳票に補正を適用すると高精度の誤りが0字から7字になりました。1°は両原稿で推定でき、誤りが減る組み合わせがあったため、下限を0.8°としました。スコアの0°比は、鮮明版・台形歪みのみ・ぼけと圧縮のみがすべて1.00倍、1°では本文が2.05倍、帳票が12.14倍でした。0°比を1.20倍超とし、別の傾きも同程度に現れる場合を除くため、競合する角度に対しても1.08倍の差を求めました。逆向きの罫線が同程度にある試料は単体テストで補正を見送ることを確認しました。鮮明版と単独劣化の対照試料は補正せず、採用した回転のみの試料の角度誤差は最大0.1°でした。H2・F3は閾値を決めた後に比較しました。

補正画像は画素寸法と認識時のdpiを保ち、Tesseract はこの画像で既存の二値化選択・認識経路を実行します。文字層には逆回転を掛けて元ページに配置します。傾いた帳票では、ビューアが欄間の空白を落とす場合があるため、離れた欄の境界に既存の不可視マーカーを置きます。

### 処理時間
