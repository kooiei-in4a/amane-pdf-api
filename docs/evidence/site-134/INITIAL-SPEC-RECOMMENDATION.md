## 1. 登録情報の推奨

文字上限はUTF-16 code unit。受理する文字は既存フォントの文字表にあるBMP文字に限定するため、通常は1文字＝1 unit。各行にLFを含めず、配列をLFで結合する。全空白行・空文字・nullは拒否し、任意項目は省略する。

| 会社登録key | 必須の推奨 | 型・上限の推奨 | 表示先／根拠 |
| --- | --- | --- | --- |
| `nameLines` | 必須 | string配列1〜2行、各1〜20文字、LF結合後41文字以内 | issuer。v0.1の`name`を置き換える改訂案。名称を省略せず2行表示できることを追加検証。 |
| `addressLines` | 必須 | string配列1〜2行、各1〜20文字、結合後41文字以内 | address。旧「各16・合計32」では16＋16＋LFが上限超過するため改訂。住所・建物名を呼び出し元が分ける。 |
| `registrationNumber` | 任意 | string、`T`＋ASCII数字13桁 | registration。実在確認はしない。 |
| `contact` | 任意 | string、1〜16文字・1行 | contact。初版は短い連絡先向け。長いメールアドレスの一般的な対応を保証する値ではない。 |
| `bankTransferLines` | 任意 | string配列1〜3行、各16文字以内、結合後48文字以内 | 請求書bankのみ。振込先がなくても生成できる。3行とも16文字は合計50になるため不可。 |
| `logoAssetId` / `sealAssetId` | 任意 | 文字列の参照ID。ASCII英数字・`_`・`-`、1〜64文字を暫定推奨 | 描画上限ではなく参照契約の案。画像binary／URLは発行JSONに含めない。 |

会社名と住所の必須性は帳票の発行元を明示するための製品上の推奨。PDF API自体の必須条件ではない。登録番号・電話・銀行・画像を一律必須にしない。未指定の任意欄は値とラベルを両方省く。画像なし／片方のみの最終帳票と任意ラベル省略の組み合わせは、採用後の小さな確認が残る。

`nameLines`は帳票に印字する完成済みの名称行とする。自動分割・会社名の短縮・敬称補完はしない。既存`name`と併存させる互換仕様はまだ作らない。未実装のv0.1案を改訂するかを決めてからJSON例と検証スクリプトをそろえる。登記名の別管理、住所検索等の製品設計は今回追加しない。

## 2. 発行入力の必須・型・上限の推奨

| key | 必須の推奨 | 型・上限／扱い |
| --- | --- | --- |
| `companyId` / `templateId` | 必須 | 文字列参照。会社の登録情報を1つのスナップショットとして解決。templateは標準請求書／見積書を選択。ID形式・版指定は後続契約で確定。 |
| `currency` | 必須 | string、`JPY`のみ。初版は税抜金額・税率8%／10%に限定する推奨。 |
| `recipient.nameLines` | 必須 | string配列1〜2行、各1〜20文字、LF結合後41文字以内。敬称を含む完成した表示。v0.1の`recipient.name`を置き換える案。 |
| `issueDate` | 必須 | 実在する日付string `YYYY-MM-DD`。発行日。取引日から補完しない。 |
| `number` | 必須 | string、1〜16文字・1行。呼び出し元の確定番号。自動採番・一意性検査はしない。 |
| `subject` | 任意 | string、1〜16文字・1行。長い件名の一般対応は対象外。 |
| `paymentDueDate` | 請求書で任意 | 実在する日付string。見積書で指定したらエラー。 |
| `validUntil` | 見積書で任意 | 実在する日付string。請求書で指定したらエラー。 |
| `transaction` | 請求書で必須、見積書で任意 | dateまたはperiodの排他指定。必須性は業務判断として採否を残す。 |
| `items` | 必須 | object配列1〜8件。順序維持。0／9件以上はエラー。 |
| `items[i].name` | 必須 | string、1〜17文字・1行。8%の表示記号※を加えた最終文字列は18文字まで。 |
| `items[i].quantity` | 必須を継続提案 | **string**。採用済み：整数部最大5桁・小数部最大3桁、最大9文字、小数点揃え。`2.50`を保持。 |
| `items[i].unitPrice` | 必須 | 非負JSON整数、0〜99,999,999円。 |
| `items[i].taxRate` | 必須 | JSON整数、8または10。既定値で補完しない。 |
| `items[i].amount` | 必須 | 非負JSON整数、0〜999,999,999,999円。確定した税抜明細金額。 |
| `taxSummary["10"]` / `["8"]` | 両方必須 | それぞれobject、`taxableAmount`と`taxAmount`を必須にする。該当なしも呼び出し元が0を明示。 |
| 上記の`taxableAmount` / `taxAmount` | 必須 | 非負JSON整数、0〜999,999,999,999円。 |
| `totalAmount` | 必須 | 同じ非負JSON整数範囲。確定合計。 |
| `notesLines` | 任意 | string配列。各行1〜16文字、取引情報込み3行・48文字以内。備考なしは省略または`[]`。配分は次節。 |

数量の整数部／小数部の上限は採用済み。`(0|[1-9][0-9]{0,4})(\.[0-9]{1,3})?`への全体一致で桁を別々に検査し、末尾0を保持する。`"123.45"`／`"12345.000"`／`"99999.999"`も受理する方針。整数部6桁・小数部4桁は拒否。数量0／負数を対象外とする正の数量案、単位欄を初版に追加しない案は引き続き業務判断の対象。

金額の小数・指数表記・数値文字列は拒否し、丸め・換算・数量との乗算・税計算・合算・整合性比較をしない。単価上限とその他金額上限は前回の実PDFで桁落ちなく抽出できた。業務上の妥当性から導いた最大取引額ではない。0円は表示、負数値引き・返金・外貨・税込入力・非課税等は初版対象外を推奨し、代表用途に必要なら対象外のまま承認しない。

JSON全体64KiBを初版候補上限として維持するが、境界の実HTTP試験は未実施。fieldsへの変換後もAPIの200項目・1項目200文字／5行・1ページ100行要素・64KiBを別に確認する。JSONの型・文字数だけで成功保証しない。

## 3. 取引情報と備考の配分

**初版は既存notesを「取引・備考」にする共有枠を推奨。** 固定8明細・1ページのまま前回の実PDFで成立した。発行日、支払期限／有効期限の欄はそれぞれ独立して保持する。

| 入力 | 取引情報の表示 | 自由備考の上限 | 確認済み境界 |
| --- | --- | --- | --- |
| `transaction.date` | `取引日 2026/10/20`の1行 | 16文字×2行 | 14＋16＋16＋LF2＝48文字、3行。 |
| `transaction.period` | `取引期間`＋`2026/12/31～2027/01/01`の2行 | 16文字×1行 | 4＋21＋16＋LF2＝43文字、3行。両端の年を保持。 |
| transaction省略（見積書の候補） | なし | 最大3行、結合後48文字 | 16＋16＋14＋LF2＝48文字。**16文字×3行ではない。** |

periodは`start`と`end`を両方必須、実在日付、start≦end。dateとの両指定はエラー。取引日／期間と発行日・期限の前後関係を新たな金額業務ロジックのように判定する仕様は加えない。期間が同日でも入力どおり期間で表示する。

超過時は、例えば期間＋備考2行なら`/notesLines/1`の`notes-budget-exceeded`で拒否する。取引情報を落とす、備考を削る、文字を縮めることで成功させない。自由備考3行を常に必要とする用途なら、**独立した取引欄のレイアウト検証が必要**。共有枠のまま両方を約束しない。

## 4. 長い会社名・宛先情報

推奨する最小のテンプレート調整は、invoice／estimateの`issuer`・`recipient`・`address`の幅を`.29→.34`とし、名称2欄をmultiline・2行・maxLength41にする。住所もmaxLength41へ。フォント9pt・既存x/y/高さは維持する。2行名の必要高さ19.8ptは元の高さ21.892pt内に収まる。幅202.3ptに対し全角20文字は最大180pt程度で、実測でも表示・文字抽出が成功した。全体の位置・罫線・8明細・合計・画像は移動しない。

これは検証用コピーの調整案。製品では`definition.json`だけを直接書き換えず、生成元・PDF・定義・hash manifestと関連する検証をそろえる。元の指定は[site生成元](https://github.com/kooiei-in4a/amane-tools-site/blob/e08aed241245f9f84a7336302edcb7d6a89a57b1/scripts/make-pdf-templates.mjs#L26)、幅／高さの判定は[API描画処理](https://github.com/kooiei-in4a/amane-pdf-api/blob/465088ed0b575f055beb6851e98d28ed22fb9928/src/Amane.Pdf.Api/FillTemplateFields.cs#L119)に根拠がある。

```json
{
  "recipient": {
    "nameLines": ["架空日本事業支援企画開発株式会社", "営業企画部 御中"]
  }
}
```

- 部署・担当者・敬称も印字行に含めるなら、すべて2行・各20文字の予算内。長い会社名で2行使えば部署用の追加行はない。会社名の途中を省略して場所を作らない。
- 初版は**宛先住所を独立key／欄として持たない**案を推奨する。今回の既存欄・追加検証には表示先がない。郵送用途や宛先住所を載せる代表用途が必要なら、この対象外案を採らず、`recipient.addressLines`等の専用欄を含む小さなレイアウト検証を追加する。
- 部署・担当者を構造化して別keyで受けるかも未確定。初版の表示行案を採るなら未知keyとして明示拒否し、受け取って捨てない。宛先住所を会社側のaddressへ誤って入れない。
- 40文字超、3行、未対応文字は元入力path付きのエラー。𠮷等を別字に置換しない。結合濁点の自動正規化もしない。対応文字の拡張が代表用途に必須と確認された場合に限り、API変更の要否を別途判断する。

## 6. エラーと採用後の完成条件

エラーは元入力のJSON Pointerを示す推奨を維持する。改訂後の例は`/recipient/nameLines/1`のtoo-long、`/items/8`のtoo-many-items、`/transaction/period/end`のinvalid-period、`/notesLines/1`のnotes-budget-exceeded。登録情報の不備は発行入力の`/companyId`と登録元`source.path=/nameLines/1`等の両方を示す。型の自動変換・trim・置換・縮小・自動改行はしない。

400（壊れたJSON・未知／重複key）、422（必須・型・上限・未対応文字・枠超過）、413（容量）の区分はsiteの**候補契約**。実PDF APIは枠超過422、未対応文字／空文字400であり、これを変更する提案ではない。[前回の入力エラー資料](standard-json-validation/README.md)と区別する。

採否を決めた後、製品実装の前に#134で次をそろえる。

1. D1〜D4の決定を記録し、標準JSONの例・項目対応・必須／型／上限・対象外・エラー例を同じ改訂版へそろえる。現行v0.1 validatorを改訂案対応済みと扱わない。
2. 採用する定義コピーで、改訂JSONから請求書／見積書の1・8明細を再生成。1／2行名・会社住所・取引日／期間・備考の境界、明細・確定金額の保持、透過画像を確認する。住所専用欄を採る場合はその表示先も確認する。
3. 改訂部分の上限超過・未知keyを、元入力path付きでPDF生成前に拒否できることを検証スクリプトで示す。任意欄省略・画像なし／片方のみも少数ケースで確認する。製品HTTPの試験と混同しない。
4. 品質は1ページ・全入力由来文字の抽出一致・欠け／重なりなし・透明度／比率／配置保持。既存の仮目安（逐次3回10秒以内、同時2件は各20秒以内、2MiB以内）は代表用途の採用基準として採否を記録する。本番SLAとはしない。既存の実測は単独約0.6秒・約220KiB、同時2件は初期検証約1秒／件で、異なる入力・測定条件を混ぜない。

**A：既存APIで対応可能。B：標準入力の採否・siteマッピング／事前検証・テンプレート調整が必要。C：今回も具体的なAPI変更の必要性は確認なし。** 新規API Issue・製品実装は開始しない。上記の確定と改訂版の検証を残したまま#134を閉じない。
